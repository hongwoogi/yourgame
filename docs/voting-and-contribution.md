# 투표와 기여도 설계

상태: 2026-08-31 사용자가 다른 참여자의 제안에 찬반 투표하고, 실제 반영 성과를 기여도와 리더보드로 보여주는 방향을 요청했다. 아래에서 요청으로 확정된 방향과 수치·운영 기본값의 제안을 구분한다. 이 문서는 제품 설계이며 공개 피드·투표 API·기여도 원장·리더보드는 아직 구현하지 않았다. [참여 안전 기준](participation-safety.md)을 먼저 적용한다.

## 요청으로 정해진 방향

- 제안 후에도 다른 사람의 의견을 읽고 찬성·반대하며 참여할 수 있게 한다.
- 제안 제출 횟수와 별개로 약 3개의 투표권을 부여한다.
- 자신의 요구가 실제로 반영될 때마다 **기여도**를 얻고 공개 성과를 리더보드로 보여준다.
- 표현이 다르거나 일부만 반영되더라도 실질적인 기여가 확인되는 여러 제안자 모두 보상할 수 있어야 한다.
- 채택된 요구를 미리 지지한 투표자에게도 더 작은 기여를 인정한다.
- 찬성표가 많은 안전한 요구는 개발 선택에서 더 높은 가중치를 받는다.
- 인기·기여도·투표권으로 Teen 기준, 안전 승인, 인증이나 운영 권한을 우회할 수 없다.

이 요청은 이전의 “공개 집계 통계만 제공하고 참여자 순위는 표시하지 않음”을 확장한다. 공개 동의한 제안과 기여도 순위를 추가하되, 내부 심사 이유·개인정보까지 공개한다는 뜻은 아니다. 기존의 서로 양립하는 유효한 요구를 가급적 폭넓게 반영한다는 원칙도 유지한다.

## 화면 구성

PC의 게임 옆 패널에 `제안하기 / 다른 제안 / 내 기여도`를 둔다. 제안 입력 상태는 탭 이동으로 지우지 않는다. 모바일은 같은 패널을 9:16 게임 아래에 두고 탭·찬반 버튼을 터치로 조작한다. 긴 리더보드 때문에 게임을 가리거나 제안 작성을 강제하지 않는다.

처음에는 댓글·쪽지·외부 링크·이미지 업로드 없이 텍스트 제안, 찬반 표시, 내 반영 이력과 기여도만 제공한다. 신고는 반대표와 분리한다. 익명 방문자는 공개 동의와 안전 심사를 거친 제안을 읽을 수 있고 실제 투표에는 Google 로그인이 필요하다.

기본 제안 목록은 최신·아직 살펴보지 않은 의견을 찾기 쉽게 만든다. 인기순만으로 노출을 독점시키지 않는다. 찬성·반대 집계는 구분하되 개인별 투표 내역을 다른 사람에게 공개하지 않는다. 리더보드는 동의한 별명과 점수·반영 이력만 보여주며 비공개 참여자도 자신의 점수와 기록을 확인할 수 있게 한다.

## 투표권 기본안

다음 값은 아직 확정하지 않은 구현 추천값이다. 실제 회차 모델을 만든 뒤 적용하고, 현재의 임시 `pending` 저장값을 영구적인 투표 예산 단위로 사용하지 않는다.

| 항목 | 추천 기본값 | 이유 |
| --- | --- | --- |
| 지급 단위 | 실제 수집 회차마다 3개, 미사용분 이월 없음 | 긴 접속 시간보다 이번 변화에 대한 선택에 집중 |
| 차감 | 찬성·반대 합산 활성 투표 3개 | 찬반을 각각 3개로 주어 총 6개가 되지 않음 |
| 대상 | 다른 작성자의 현재 승인된 공개 revision에 1표 | 자기 투표, 같은 제안 양방향 투표·중복표 방지 |
| 변경·취소 | 회차 마감 전 가능. 취소는 사용 중인 슬롯 반환 | 잘못 누른 투표를 고칠 수 있음 |
| 마감 | 제안과 투표·가중치의 고정 시각을 동일하게 적용 | 결과를 본 뒤 편승하는 투표 방지 |
| 정지·비공개·안전 보류 | 새 투표 금지, 현재 선택 집계에서 제외 | 제한된 제안을 계속 밀어 올리지 못함 |
| 동시성 | 계정·회차별 원자적 예산 검사와 요청 중복 방지 | 여러 탭·기기·재시도로 3개를 넘기지 못함 |

로그인만 하거나 화면을 다시 연다고 투표하지 않는다. 비로그인 상태에서 명시적으로 누른 표를 로그인 뒤 이어갈 경우에도 회차·대상 revision·남은 표를 재확인하고 딱 한 번 처리한다. 바뀐 내용이나 이미 닫힌 회차에 조용히 표를 옮기지 않는다.

제안 수정이 접수되면 기존 공개 revision에 대한 투표를 새 내용으로 승계하지 않는 방식을 추천한다. 기존 표는 이력에 남기고 현재 집계에서 빠지며, 해당 회차가 열려 있을 때 활성 슬롯을 반환한다. 새 본문이 안전 승인되어 공개되면 참여자가 다시 판단해 투표한다. 수정 저장 전에 이 영향을 작성자에게 알린다. 이렇게 해야 안전한 문장으로 표를 모은 뒤 전혀 다른 요구로 바꾸는 일을 막을 수 있다.

## 공개 동의와 익명성

현재 접수한 제안은 본인과 관리자에게 보이는 자료다. 과거 제안을 일괄 공개하지 않는다. 작성자가 공개 화면과 공개될 내용을 미리 확인하고 동의한 revision만 피드에 게시한다. 새 제출에도 공개 여부를 분명히 알리고 공개 선택과 개발 검토 참여를 구분한다. 비공개 제안은 기존처럼 안전 검토·채택 대상이 될 수 있지만 다른 사용자의 표를 받지는 않는다.

Google의 이름·이메일·sub·프로필 사진을 공개 별명으로 자동 복사하지 않는다. 공개용 별도 식별자와 안전한 별명을 사용하고 리더보드 공개 여부도 관리할 수 있어야 한다. 탈퇴·비공개 요청 시 공개 식별자와 집계·감사 기록을 어떻게 분리할지 개인정보 운영 정책과 함께 확정한다. 이 문서가 기존 데이터의 공개 허락은 아니다.

## 유사도, 충족 여부와 점수

유사도는 **검토할 관련 요구를 찾는 도구**다. 높은 문장 유사도는 채택이나 보상의 증거가 아니다. 예를 들어 “회복 물약을 없애자”와 “회복 물약을 추가하자”는 단어가 거의 같아도 반대되는 요구다. “더 재미있게”, 게임 기능을 전부 나열한 문장, 이미 존재하는 기능을 그대로 복사한 제안에 자동 보상하지 않는다.

반영 판단은 다음 순서로 한다.

1. 안전 승인된 원문 revision과 개발용 정리문에서 구체적으로 확인할 수 있는 요구를 분리한다.
2. 같은 변화인 요구는 하나의 묶음으로 연결하고, 반대·조건부 요구는 구분한다. 같은 계정이 반복 제안해도 같은 요구의 지지와 기여가 늘어나지 않는다.
3. 공개할 게임의 변경점·실행 검증에 요구별 충족 근거를 연결한다. 원문을 읽고 점수를 주라는 지시는 근거가 아니다.
4. 실제 공개 성공 뒤 완전 반영·실질적 일부 반영·미반영을 기록한다. 유사도만 높거나 앞으로 만들 계획인 것은 미반영이다.
5. 같은 공개 버전·요구·참여자의 지급 키로 중복 지급을 막고, 여러 실제 제안자에게 각각 기여를 인정한다.

예를 들어 A가 “매번 다른 지형과 밤낮 변화”, B가 “랜덤 맵”을 제안했고 실제 게임에 지형 변화만 공개됐다면 A의 일부 요구와 B의 요구가 함께 반영될 수 있다. A만 최초 작성자라는 이유로 B를 배제하지 않는다. 반대로 C가 “랜덤 맵을 없애자”고 썼다면 같은 단어 때문에 보상하지 않는다.

최소 반영 기준은 문장의 몇 퍼센트가 겹쳤는지가 아니라 **검증 가능한 요구 하나 이상이 실제 변화에 기여했는가**다. 모호한 경우 임의 유사도 임계값으로 확정하지 않고 검토 보류한다. 모델 버전·요구 분리 기준·판정 근거를 기록하고 이의를 검토할 수 있게 한다. 유사도·반영 정도 산정 모델은 아직 연결하지 않았으며 정확도를 측정한 것처럼 임계값을 표시하지 않는다.

## 기여도 배점 추천안

아래 수치는 실제 분포를 보며 조정할 초기안이며 아직 운영에 적용하지 않았다. 점수는 현금·아이템 교환·추가 운영 권한이 없는 참여 성과다.

| 성과 | 초기 배점 제안 |
| --- | ---: |
| 구체적 요구가 충분히 반영됨 | 제안 기여 100 |
| 요구 중 의미 있는 일부가 반영됨 | 제안 기여 50 |
| 단어만 유사·이미 있던 기능 복사·미반영 | 0 |
| 마감 전에 반영 요구에 찬성함 | 해당 요구 배점의 20%, 즉 20 또는 10 |
| 반대표, 마감 뒤 찬성, 무효 투표 | 0, 반대했다고 기존 점수를 빼지는 않음 |

같은 참여자·요구 묶음에는 한 번만 지급한다. 유사 제안 세 개를 올리거나 여러 복제 제안에 표를 던져도 같은 반영 성과를 여러 번 벌지 못한다. 자신의 요구 묶음으로 제안 기여를 받는 사람이 그 묶음의 다른 글에도 찬성했다면 더 큰 제안 기여만 적용하고 투표 기여를 중복 지급하지 않는다.

회차당 3개의 활성 표라면 투표 기여 상한은 한 회차 60점이 된다. 제안 기여의 회차 상한은 초기 300점을 추천한다. 단일 글을 수십 개의 작은 요구로 쪼개는 방식도 같은 실질적 변화로 묶어야 한다. 다중 Google 계정을 자연인별로 완전히 중복 제거할 수 없으므로 신규 계정 간 집중 상호 투표·동일 내용·비정상 속도는 별도 이상 징후로 확인하고 자동으로 유죄로 단정하지 않는다.

이미 지급된 변화가 다음 버전에 그대로 남아 있다고 다시 지급하지 않는다. 이전에 미반영된 부분이 나중에 새로 충족되면 그 추가 성과만 기록한다. 기술 장애로 정상 버전에 잠시 복귀했다고 기여도를 자동 몰수하지 않는다. 허위·부정·잘못된 판정의 정정은 이유 있는 조정 원장으로 남기며 과거 지급을 삭제·재사용하지 않는다.

현재 선택 정책의 “기존 기여자” 보너스는 자기 제안이 실제 반영된 자격을 뜻한다. 투표 기여 점수만으로 이 보너스를 새로 얻거나 누적 기여도만큼 채택 가중치가 계속 커지도록 바꾸지 않는다. 리더보드 상위권이 이후 결과를 독점하는 순환을 제한한다.

## 찬반과 개발 선택의 관계

먼저 안전·로그라이크 경계·현재 버전 유효성·구현 가능성을 검사한다. 그 뒤에만 지지를 비교한다. 과격한 제안을 많은 계정으로 밀어 올려도 안전 승인·공개 검증을 건너뛸 수 없다.

기존 합의는 제안자의 기본 1점에 플레이타임과 기존 제안 기여자 보너스를 합산한다. 이를 확장할 추천안은 별도 찬성 투표자의 가중치에 0.5를 곱해 추가하는 방식이다. 같은 참여자가 같은 요구의 작성자이면서 찬성자이거나 복제된 여러 글에 투표해도 가장 큰 한 번의 지지만 반영한다. 활동 시간 검증이 아직 없다는 사실은 기존과 같다.

반대표는 초기에는 **별도 이견 지표로 표시하되 자동 감점·자동 제외에는 쓰지 않는 방식**을 추천한다. 다운보트 집단 공격으로 소수의 좋은 제안을 지우지 않고 충돌 검토의 근거로 삼기 위해서다. 반대표에도 3개 예산을 사용한다. 직접 감점 가중치는 실제 사용 결과를 본 뒤 별도 합의한다. 신고나 안전 위반 판정과 혼동하지 않는다.

안전한 요구끼리 충돌할 때 합산점수, 플레이타임 가중점수, 완전 동점 시 고정된 추첨 순서를 유지한다. 서로 충돌하지 않는 요구를 인기 상위 몇 개로 제한하지 않는다. 자동 선택·투표 가중치 코드는 아직 구현하지 않았으므로 이 추천 수식을 현재 서비스의 동작으로 표시하지 않는다.

## 필요한 데이터와 검증 순서

| 기록 | 핵심 연결과 제한 |
| --- | --- |
| 실제 수집 회차 | 고유 ID, 대상 게임, 시작·마감 시각. 임시 `pending`이나 배포 시도 ID와 구분 |
| 공개 제안 revision | 원문 revision·안전 승인·공개 동의·별도 공개 식별자. 불변 내용과 수정 이력 |
| 투표와 변경 이력 | 계정·회차·공개 revision·방향·시각·요청 ID, 활성 예산 최대 3 |
| 요구 묶음 | 관련 원문·반대 관계·중복 제거·판정 버전. 단순 텍스트 해시로 의미 동일성을 주장하지 않음 |
| 반영 판정 | 실제 공개 게임·변경점·실행 증거·충족 요구·정도, 심사자와 정책 버전 |
| 기여도 원장 | 지급·조정 이벤트, 중복 방지 키, 제안/투표 기여 구분. 클라이언트 총점 신뢰 금지 |
| 리더보드 | 공개 동의한 별명·확정 기여도만 조회. 이메일·내부 메모·미심사 본문 없음 |

첫 단계로 안전 심사와 원문 revision 보존을 넣는다. 다음에 실제 회차·공개 동의·공개용 신원·투표의 원자성을 구현한다. 실제 게임 공개 증거와 반영 판정이 생긴 뒤 원장·리더보드를 연결한다. 아직 채택 기록이 없으면 정직한 빈 상태를 보여주며 테스트 점수나 가짜 기여자를 운영에 넣지 않는다.

필수 검증에는 여러 기기의 동시 네 번째 표, 재전송 중복, 자기·정지 계정 표, 공개 동의 없는 읽기, 수정·승인·마감 경쟁, 안전 승인 철회, 중복 요구 보상, 반대 의미 오분류, 공개 실패·재시도·복귀 시 중복 지급, 점수 조작을 지시하는 본문이 포함된다.

## 구현 전 확정할 값

참여 방향과 안전 우선은 사용자 요구다. **회차당 찬반 합산 3개**, 반대의 초기 영향, 100/50·20% 배점과 제안 기여 300점 상한은 이 문서의 추천값이다. 값이 확정되기 전에 운영 투표·보상으로 조용히 적용하지 않는다. 공개 동의와 개인정보 보호, 안전 승인 우선, 실제 공개 후에만 지급, 서버 중복 방지 원칙은 수치와 무관한 기본 안전 조건이다.
