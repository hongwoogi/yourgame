# 기여도 정산 운영

최초 게임 공개와 기여도 지급은 서로 다른 결과다. 공개된 게임의 불변 검토 영수증과 실제 공개 확인이 있어도, 요구별 반영 판정과 마감 투표를 정산하지 않으면 리더보드는 0점을 유지한다. 이 경로는 누락된 정산을 신뢰된 로컬 운영자가 처리하기 위한 것이다. 게임 생성, 공개 선택, 사용자 인증이나 예약 범위는 변경하지 않는다.

작성자 식의 `**` 해석은 아직 확인 중이다. 현재 기본 정책은 `pending_confirmation`이며 운영 지급은 계속 차단한다. `weighted`와 `exponent`는 명시적인 비공개 계산 후보일 뿐이다. 사용자 확인 없이 정책 버전이나 운영 점수를 확정하지 않는다. 투표자 식은 `10 + 찬성 − 반대 × 0.5`이며 유효한 사전 찬성자만 지급 대상이다.

## 근거와 지급 단위

- 현재 선택이 실제 검증된 공개 상태여야 하고, 정확한 검토 영수증·소스/자산/런타임 바인딩·완료된 제작 실행이 일치해야 한다.
- 원문 revision과 현재 안전 승인, 개발용 정리문 바인딩이 일치해야 한다. 안전 승인이나 문장 유사도만으로 반영을 인정하지 않는다.
- 운영자는 공개 게임의 구체적인 변화와 실행 증거를 검토하고, 완전 반영 또는 실질적 일부 반영을 기록한다. 한 요구를 수십 개의 작은 묶음으로 나누거나 기존 기능을 새 성과로 다시 명명하지 않는다.
- `requirementGroupId`는 같은 의미의 요구 묶음이고, `fulfillmentId`는 새로 검증된 실제 변화의 안정적인 식별자다. 새 배포 시도·재공개·롤백·묶음 이름 변경은 새 성과가 아니다. 동일 성과/참여자는 원장의 전역 고유 제약으로 다시 지급하지 못한다. 모든 의미 식별자를 임의로 새로 붙이는 행위까지 문자열 해시로 판별할 수는 없으며, 이 판단은 운영자 검토 책임이다.
- 같은 묶음의 작성자와 찬성자는 참여자별로 중복 제거한다. 작성자이면서 찬성자이면 더 큰 한 점수만 지급하고 작성자 채택 사실은 보존한다. 같은 사람이 묶음 안에서 찬성과 반대를 함께 남겼다면 임의 상계하지 않고 검토를 중단한다.
- 일부 반영 50점, 회차 300점 상한, 0점 하한은 적용하지 않는다. 점수는 정수로 표현한 0.5점 단위로 정확하게 계산한다.

## 마감 투표

`server/contribution-votes.mjs`는 실제 종료된 회차와 정확한 본문/공개 revision, 회원 제어, 운영 검토, 불변 투표 이벤트 및 요청 영수증을 한 읽기 스냅샷에서 대조한다. 취소·자기표·당시 무효 표를 제외하고, 채택 입력 밖의 제안까지 포함해 회차당 활성 3표 예산을 검증한다. 현재 피드 수치를 과거 마감 스냅샷으로 표시하지 않는다.

마감 뒤 안전 심사나 로그인만으로 당시 유효 표를 없애지 않는다. 그 외 마감 이후 상태 변경은 원칙적으로 정산을 중단한다. 예외적으로 운영 검토의 최초 변경만 마감 이후 발생했음을 revision 2, 단일 감사 기록, 정확한 요청 해시·응답·시각으로 증명할 수 있으면, 마감 당시의 기본 `pending`/revision 1 상태를 사용한다. 여러 번 바뀌었거나 증거가 불완전하면 상태를 추정하지 않는다. 원본 투표·이력은 수정하지 않는다.

## 로컬 운영 순서

`docs/launch-runbook.md`의 자격증명·관측·배포 규칙을 먼저 적용한다. `admin-worker.mjs status`로 서비스 상태를 읽고, 기존 정산 영수증과 원장을 확인해 중복 작업을 피한다. 원문, 계정 식별자, 비공개 해시, 감사 이유, 환경값은 출력하거나 Git에 넣지 않는다.

1. `.local`에 정확한 제작/공개/입력 바인딩과 요구 묶음을 담은 정산 계획을 준비한다. 별도의 운영자 반영 검토 파일에는 실제 구현, 근거 파일, 한계를 적는다. 계획은 그 검토 파일의 바이트 해시와 각 판정의 정규화 해시를 연결한다. 생성된 역할 보고서는 참고 자료이며 스스로 승인할 수 없다.
2. 아래 `preview`로 실제 DB 근거를 다시 검증하고 비공개 지급 후보를 저장한다. 미리보기는 스키마나 원장을 쓰지 않는다. 출력에는 묶음 수·건수·총점만 나온다. 실제 반영 여부를 검토하지 않은 파일을 도구에 넘기는 것은 승인 절차가 아니다.
3. 확인된 식으로 정책 버전을 확정한 뒤 관련 단위·UI 검사를 통과하고, 명시한 파일만 커밋한다. 그 커밋의 새 `git archive`에서 설치·빌드를 통과시킨다. 공유 작업의 미완료 파일이나 `.local` 자료를 포함하지 않는다.
4. 실제 운영 검증과 서비스 revision 확인 후 `prepare`를 한 번 실행한다. 기존 원장은 그대로 두고 정산 영수증/메타 테이블과 성과·사용자 고유 인덱스만 추가한다. 일반 DB 초기화나 사용자 데이터 삭제를 대신 실행하지 않는다.
5. 같은 검토와 계획으로 `apply`한다. 실제 공개·입력·투표·정책을 쓰기 트랜잭션 안에서 다시 검사하고, 원장과 감사 기록 및 정산 영수증을 함께 저장한다. 브라우저나 관리자 JSON에는 발행 액션을 추가하지 않는다.
6. 실제 공개 리더보드/개인 점수의 합계와 영수증을 대조하고, 보호해야 할 업무 데이터 및 기존 게임이 유지됐는지 검증한 뒤 지급 완료로 기록한다. 정책 배포나 HTTP 200만으로 정산 성공을 보고하지 않는다.

```powershell
node --env-file=.env.production.local scripts/operator-contribution-settlement.mjs preview --plan .local/settlement/plan.json --review .local/settlement/review.json --output .local/settlement/preview.json
node --env-file=.env.production.local scripts/operator-contribution-settlement.mjs prepare --service-revision 1
node --env-file=.env.production.local scripts/operator-contribution-settlement.mjs apply --plan .local/settlement/plan.json --review .local/settlement/review.json --output .local/settlement/receipt.json
```

위 경로와 revision은 예시다. 실제 파일과 관측한 revision을 사용한다. 명령은 기존 결과 파일을 덮어쓰지 않는다. 커밋 응답이나 로컬 영수증 저장에 실패하면 효과가 불확실할 수 있으므로 새 요청 ID를 만들거나 자동 재시도하지 않는다. 원래 계획·요청 ID와 불확실한 결과 파일은 보존하고, **새 미사용 `--output` 경로**로 DB 영수증·원장을 대조한다. 정확한 동일 요청 재실행은 기존 결과만 확인하며 `issuedCount=0`, `replayed=true`를 반환한다. `CONTRIBUTION_OUTPUT_EXISTS`는 DB 조회 전에 멈추며 `reconcileRequired=true`를 표시한다. 그 호출의 `effectUncertain=false`가 이전 지급도 없었다는 뜻은 아니다.

## 현재 한계

이 경로는 수동 운영 정산이며 기존 관측 또는 제작 heartbeat를 점수 발행 자동화로 바꾸지 않는다. 정책 확인, 실제 회차, 반영 검토와 공개 증거가 없는 다음 회차에 자동 점수를 만들지 않는다.

기존 리더보드의 최대 50,000행 정확 집계를 유지한다. 발행 때문에 이 읽기 범위를 초과할 수 있으면 정산을 사전에 중단한다. 이는 점수 상한이 아니라 관측 용량 한계다. 더 큰 운영 규모에는 별도로 검증한 누적 조회 모델이 필요하다. 잘못된 정산을 삭제하거나 덮어쓰는 정정 기능은 제공하지 않으며, 정정이 필요하면 감사 가능한 별도 조정 원장을 설계해 사용자와 처리한다.
