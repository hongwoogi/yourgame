# 공동 진화 게임 — 설계 인터뷰 기록

상태: 이번 준비 화면과 제안 접수 범위의 설계 합의를 마치고 구현 중이다. 최초 모집은 접수 기능 제공 즉시 시작하고 2026-08-31 23:00 한국시간에 마감하며, 2026-09-01 00:00을 첫 게임 공개 목표로 확정했다. 로그인·제안 접수·장애 감시의 구현과 검증 상태는 각각의 운영 기록에서 구분한다. 전체 게임과 자동 진화의 미정 사항을 모두 확정했다는 뜻은 아니다.

## 출발점

빈 캔버스에 여러 사람이 제한된 기여를 쌓는 공동 창작에서 착안했다. 일정 시간 동안 사용자 프롬프트를 모으고 로컬 PC의 Codex로 게임의 변화를 구현한다. 구성은 GitHub, Vercel, Turso 무료 플랜이며 PC에서 검증된 코드를 GitHub에 올리면 Vercel의 Git 연동으로 배포한다. 대표 도메인은 사용자가 Cloudflare를 통해 구매한 yourga.me다. GitHub·Vercel·Turso 연결과 도메인의 DNS·HTTPS 검증을 마쳤으며 현재는 준비 페이지를 제공한다.

2026-08-30 사용자가 회원가입과 도메인 구매 완료를 알렸고, 2026-08-31 CLI로 접근 가능한 연결을 처리했다. 자세한 명령과 검증 결과는 [인프라 연결 상태](infrastructure-status.md)에 기록했다.

계정 준비 완료를 리소스 연결 완료로 간주하지 않는다. API 토큰, 비밀번호 또는 DB 인증 정보를 대화나 설계 문서에 기록하지 않는다. 도메인 선택만으로 생성 게임과 계정·관리자 기능의 실행 경계가 결정된 것은 아니며, 구체적인 서브도메인 구성은 별도 설계 대상이다.

## 첫 개발 범위 — 2026-08-31

이번 사용자 요청으로 확정된 내용:

- 당장 추가할 화면 요소는 카운트다운, 대략적인 프로젝트 설명, 제안 입력창과 로그인 버튼이다. 게임 화면·공개 통계·운영자 대시보드는 이번 화면 범위에 포함하지 않는다.
- 로그인한 참여자는 최근 60분 동안 최대 3개의 제안을 신규 제출할 수 있다. 정각·재로그인·회차 변경으로 횟수를 초기화하지 않고, 각 접수로부터 60분이 지나면 해당 횟수가 돌아온다. 제안 하나의 길이는 2,000바이트 이하다. 기존의 수집 회차당 제안 1개 제한은 이 요구로 대체한다.
- 접수한 제안은 수정할 수 있으며 삭제 기능은 제공하지 않는다. 수정 가능 시점은 기존 합의대로 해당 수집 회차 마감 전까지다.
- 비로그인 참여자도 제안 초안을 입력할 수 있다. 전송을 시도하면 로그인 모달을 표시하고, Google 로그인 성공 후 남은 제출 횟수가 있으면 전송하려던 제안을 자동 제출한다. 0회이면 초안을 보존하고 다음 제출 가능 시각을 안내한다. 횟수가 돌아온 뒤에는 사용자가 다시 전송을 눌러야 하며 자동으로 전송하지 않는다.
- 로그인은 Google만 제공한다. 사용자가 제공한 웹용 OAuth 2.0 클라이언트를 사용하고 별도의 비밀번호 회원가입은 제공하지 않는다. 키 값과 클라이언트 비밀키는 문서·코드 저장소에 기록하지 않는다.
- 최초 제안 모집은 접수 기능이 실제 제공되는 즉시 시작한다. 2026-08-31 23:00 한국시간(UTC 2026-08-31 14:00)에 최초 제안을 확정하고 1시간 동안 제작·검증하여, 2026-09-01 00:00 한국시간(UTC 2026-08-31 15:00)에 첫 게임 공개를 목표로 한다. 최초 모집에는 이전의 3시간 고정 규칙을 적용하지 않는다. 카운트다운은 첫 게임 공개 목표를 가리킨다. 아직 구현·배포되지 않은 접수 기능을 이미 개시했다고 표시하지 않는다.
- 실패가 확인되면 운영자에게 이 작업에서 원인·영향·현재 조치를 알리고 복구를 계속한다. 실패를 숨기거나 검증을 건너뛰어 공개하지 않는다. 실패가 절대 없다는 보장, 운영자 응답 없이도 모든 장애를 해결한다는 보장, 알림이 항상 실시간 도착한다는 보장은 하지 않는다.
- 사용자는 운영 PC를 항상 켜둘 예정이다. 이 운영 전제만으로 로컬 작업자가 설치되었거나 자동 실행이 검증되었다고 간주하지 않는다. 예외적인 장애·구독 한도 부족에 대한 기존 운영 지연 정책은 유지한다.

위 요구와 기존 합의를 구체화하는 구현 기본값:

- 여러 제안은 각각 별도 접수로 저장한다. 같은 참여자의 반복 제출로 동일 요구의 지지 점수를 늘리지 않는 기존 원칙은 유지한다.
- 수정은 신규 제출이 아니므로 제출 횟수를 차감·환급하지 않고 최초 접수 시각도 바꾸지 않는다. 마감되어 확정한 제안은 변경하지 않으며, 이후 변경 요청은 다음 회차의 신규 제안으로 받는다. 수정 접근점은 입력창 근처의 본인 제안 목록으로 한정한다.
- 길이는 신규 제출과 수정 모두 UTF-8 기준으로 검사한다. 화면뿐 아니라 서버에서도 2,000바이트 제한을 확인하고 공백뿐인 입력은 거절한다.
- 횟수는 서버에서 저장에 성공한 신규 접수만 계산한다. 전송 재시도·중복 클릭은 같은 접수의 중복 저장이나 중복 차감을 일으키지 않도록 처리한다. 동시 요청도 서버에서 제한한다.
- 로그인 취소·실패·접수 실패 시 초안을 지우지 않는다. 로그인 버튼만 누른 경우에는 자동 제출하지 않고, 전송 시도 때문에 로그인한 초안만 제출을 이어간다. 실제 저장 성공을 확인한 뒤에만 접수 완료를 안내한다.

Q6 수락으로 최초 모집 마감과 첫 공개 목표의 관계를 확정했다. 마감 후 들어온 신규 제안은 다음 회차 대기로 접수하고 최초 회차의 확정된 내용을 바꾸지 않는다. 실제 게임 공개 전에는 다음 버전 번호나 다음 공개 성공을 시간만으로 만들어내지 않는다. 카운트다운이 0이 되어도 실제 게임 공개가 확인되지 않았다면 준비·지연 상태를 표시한다. 예약 실행의 등록 여부와 실제 성공은 별도로 확인한다.

Google OAuth 값의 보관과 제공자 설정 확인은 [Google 로그인 준비 상태](google-login-setup.md)에 기록한다. 이 절은 요구사항과 구현 기본값의 기록이며, 기능 구현·검증·배포 완료를 뜻하지 않는다.

## 확정된 방향

- 성공의 핵심은 개인들의 방향성이 서로 정합되어 게임이 나아지는 것이다.
- 솔로플레이만 지원한다. 개인별로 서로 다른 게임을 생성하지 않는다. 이전 버전도 플레이할 수 있어 동시에 여러 공개 버전의 플레이가 가능하다.
- 지원 기기는 PC 브라우저로 한정한다. 모바일은 게임 플레이, 제안 제출 및 통계 화면을 포함해 지원 범위에서 제외한다.
- 게임의 규칙은 빈 캔버스에서 출발하고 점차 정교해진다.
- 최초 제안 모집은 접수 기능이 제공되는 즉시 시작하며 2026-08-31 23:00 한국시간에 마감한다. 1시간의 제작·검증 뒤 2026-09-01 00:00 한국시간의 첫 공개를 목표로 한다. 최초 모집의 3시간 고정 규칙은 적용하지 않는다. 첫 화면은 빈 캔버스, 로그라이크라는 공통 조건, 제안 입력과 카운트다운으로 구성한다. 유효한 제안이 없으면 임의로 게임을 만들지 않고 최초 모집 연장을 운영자에게 알린다.
- 첫 게임은 최초 모집 요구를 바탕으로 만들며 검증을 통과한 경우에만 v1으로 공개한다. 제작·검증 1시간은 첫 공개를 목표로 확보한 시간이며, 검증에 실패한 게임을 시간에 맞추기 위해 공개하지 않는다.
- 기본 장르는 로그라이크로 유지하며 초기 목표 플레이타임은 한 판 5~10분이다. 장르 안에서 전투 방식, 목표, 성장 구조를 포함한 나머지 게임 요소는 이후 버전에서도 참여자 제안으로 변경할 수 있다.
- 제안을 받는 대로 모두 반영하지 않는다. 게임의 보호 경계는 로그라이크 장르이며, 장르를 벗어나는 제안은 자동 제외한다. 기존의 핵심 구조를 바꾼다는 이유만으로 제외하지 않는다.
- 한 버전에 최대 3개만 반영하자는 추천은 채택하지 않았다. 개수 제한보다 유효하고 서로 양립하는 요구를 가급적 모두 반영하는 것을 목표로 한다. 플레이에 영향 없는 단독 꾸미기 요청은 묶어 후순위로 두고, 버그 수정이나 조작 불편 개선은 규모가 작아도 반영 대상으로 둔다. 지지자가 적다는 이유만으로 제외하지 않는다.
- 구현 시간 안에 모든 요구를 처리하지 못하면 완성되고 함께 검증된 변경만 공개한다. 나머지 유효 요구는 다음 회차에서 재검토하며 자동 반영을 약속하지 않는다.
- 이월된 요구의 내용은 작업 후보로 보존하지만 과거 회차의 지지 점수는 누적하지 않는다. 최신 게임에서도 유효한지 재검토하며 충돌할 때는 현재 회차 피드백을 우선한다.
- 요구의 지지는 서로 다른 참여자 수를 기준으로 집계한다. 참여자당 기본 1점에 플레이타임 보너스 최대 0.1점, 기존 기여자 보너스 0.1점을 더해 최대 1.2점으로 계산한다. 같은 참여자가 같은 요구를 반복 제출해도 참여자 수가 늘어나지는 않는다.
- 충돌하는 요구는 합산점수가 높은 쪽을 우선한다. 합산점수가 같으면 그 요구의 플레이타임 가중점수가 높은 쪽을 우선한다. 점수가 다른 요구끼리 가중 추첨하는 방식은 사용하지 않는다. 두 비교값까지 모두 같은 완전 동점에만 앞선 추첨 합의를 적용하며, 최초 생성과 후속 버전을 구분하지 않는다. 자세한 정의와 예시는 [충돌 선택 규칙](selection-policy.md)을 따른다.
- 기존 기여자는 제안이 실제 게임에 한 번 이상 반영된 참여자이며, 자격과 보너스는 버전이 바뀌어도 유지된다. 플레이타임 보너스는 현재 최신 버전의 활동 시간에 비례하여 30분에서 0.1점에 도달한다. 새 버전이 공개되면 이 시간은 새로 쌓는다.
- 플레이는 로그인 없이 허용하며 제안 제출은 Google 로그인이 필요하다. 참여자별 최근 60분 동안 신규 제출 최대 3개, 제안 하나당 2,000 UTF-8 바이트로 제한한다. 해당 수집 회차 마감 전에는 제안을 수정할 수 있으며 삭제는 제공하지 않는다. 수정은 신규 제출 횟수를 바꾸지 않는다. 비로그인 상태에서 전송을 시도하면 로그인 모달을 표시하고 로그인 성공 후 남은 횟수가 있을 때 자동 제출한다. 0회이면 초안을 보존하고 다음 가능 시각을 표시하며 사용자가 나중에 다시 전송한다. 로그인만으로 서로 다른 자연인임을 증명한다고 가정하지 않는다.
- 정규 배포 1시간 전에 해당 수집 회차를 마감하고 제안과 가중치를 확정한다. 이후 접수되는 제안은 다음 회차로 보낸다. 정시까지 공개 가능한 변경 묶음의 검증이 끝나지 않으면 기존 공개 버전을 유지한다. 일부 요구만 완료된 경우에도 그 묶음 전체를 검증한 뒤에만 공개한다.
- 업데이트는 정해진 시간에만 이루어진다. 초기 간격은 3시간이며 실제 공개에 성공한 버전 4개마다 간격을 1시간 늘린다. 최초 공개는 v1이며 v4 공개 이후 4시간, v8 공개 이후 5시간 간격이다. 실패하거나 반영할 제안이 없는 회차는 버전을 올리지 않고 기존 간격으로 다음 기회를 기다린다.
- 세이브, 아이템, 설정은 로컬에 저장한다. 계정, 프롬프트, 채택 이력, 최소 플레이 확인 기록은 중앙 DB에 저장한다.
- 중앙 DB는 직접 서버를 운영하지 않는 무료 온라인 관리형 서비스를 사용한다. 사용자의 Supabase 프로젝트 한도는 이미 소진되어 있어 이 프로젝트의 후보에서 제외한다. 기존 DB 프로젝트 재사용을 전제로 하지 않는다.
- 관리형 DB는 Turso의 무료 플랜을 사용한다. 직접 가입 요금표에서는 Free, 현재 Vercel 연동 CLI에서는 Starter 월 $0로 표시된다. 유료 플랜이나 초과 사용 플랜은 선택하지 않는다. GitHub는 코드와 버전 이력, Vercel은 사이트와 서버 API, 개인 PC의 Codex는 요구 처리와 게임 변경을 담당한다. GitHub·Vercel·Turso DB 연결을 완료했으며 실제 게임 데이터 스키마는 아직 만들지 않았다.
- 대표 도메인은 yourga.me를 사용한다. Cloudflare 네임서버를 유지한 상태로 Vercel에 연결했으며, DNS 검증과 HTTPS 정상 응답을 확인했다.
- Vercel Cron을 사용하지 않는다. 개인 PC가 처리 시점을 관리하고 코드 생성과 로컬 검증을 수행한 뒤 GitHub에 올리면 Vercel Git 연동이 배포를 시작한다. 사용자는 PC를 항상 켜둘 예정이다. 사용자가 말한 '수동 배포'는 Vercel 예약 실행 대신 PC 측 동작으로 배포를 유발한다는 뜻으로 기록하며, 매 회차 사람의 클릭이나 승인을 요구하는 것으로 해석하지 않는다.
- 운영자 대시보드에서 제안, 집계 점수, 채택 이유, 배포 결과와 비용을 확인한다. 운영 기능은 일시정지, 안전 문제 제안 차단, 실패 재시도, 이전 버전 복구이며 개입 이유를 기록한다. 평상시 변경 과정은 자동 진행한다.
- 참여자 공개 화면에는 어떤 요구가 얼마나 있었는지 집계 통계만 제공한다. 순위와 제외 사유는 공개하지 않는다. 운영자용 판단·감사 기록과 참여자 공개 정보는 구분한다.
- 하루 추가 AI 비용 상한은 1,000원이다. 사용자는 별도 유료 API 대신 기존 Codex 구독 환경을 이용해 자신의 컴퓨터에서 요청을 처리하는 방식을 원한다. 이는 구독 한도 내 실행을 전제로 하며, 구독의 사용량과 추가 비용을 같은 값으로 취급하지 않는다.
- PC 응답 없음, 구독 사용량 부족이나 검증 실패가 확인되면 검증하지 않은 변경을 공개하지 않고 기존 게임이 있으면 유지한다. 운영자에게 알린 뒤 가능한 복구를 바로 진행하며 다음 정규 회차까지 아무 조치 없이 기다리지 않는다. 공개 일정·버전 집계는 실제 검증과 공개 성공을 기준으로 하며, 유료 API 전환이나 추가 크레딧 구매로 자동 복구하지 않는다. 기술적으로 크레딧 자동 소모까지 차단할 수 있는지는 별도 검증 대상이다.
- 운영자 대시보드와 참여자 화면에 운영 문제로 반영이 지연되고 있음을 표시한다. 참여자용 안내는 운영자를 가볍게 놀리는 유머를 사용하되 실제 원인, 현재 게임 이용 가능 여부와 확인된 다음 시도 시각은 명확히 구분한다. 구체적인 문구와 노출 규칙은 [운영 상태 안내](operations-status.md)를 따른다.
- 새 버전 배포 이후에도 이전 버전을 플레이할 수 있도록 아카이브를 제공한다.
- 아카이브는 플레이 전용으로 제공하고 과거 버전을 수정하는 제안은 접수하지 않는다. 제안은 최신 버전을 대상으로만 접수하며 과거 공개 버전 자체는 보존한다.
- 버전별 세이브는 독립적으로 유지한다. 새 버전은 새 진행으로 시작하며 이전 진행은 아카이브의 해당 버전에서 이어간다.

## 확정된 계산 규칙

- 참여자 가중치 = 1 + 0.1 × min(최신 버전 활동 시간(분) / 30, 1) + (기존 기여자이면 0.1, 아니면 0). 활동 시간은 음수가 아닌 검증 대상 기록이며, 수집 마감 시의 제안·자격·활동 시간을 집계 스냅샷으로 확정한다. 활동 시간 검증의 구체적 방법은 미정이다.
- 요구의 합산점수는 해당 요구를 지지하는 서로 다른 참여자의 가중치 합계다. 동점 판단용 플레이타임 가중점수는 같은 참여자들의 플레이타임 보너스만 합한 값이며, 원시 플레이 시간이나 가장 오래 플레이한 한 사람의 시간이 아니다.
- 공개 성공 누적 수가 N일 때 다음 업데이트 간격 = 3 + floor(N / 4)시간. v1을 공개한 이후부터 적용한다. 최초 모집은 즉시 시작, 2026-08-31 23:00 한국시간 마감이며 첫 게임 공개 목표는 2026-09-01 00:00 한국시간이다. 첫 회차에는 모집 3시간 고정 대신 이 절대 시각을 적용한다.
- 운영자 재시도는 정규 공개 일정과 구분한다. 재시도 또는 복구를 눌렀을 때 공개 시각과 버전 집계에 미치는 세부 동작은 미정이다.

## 아직 결정하지 않은 사항

- 최초 모집에 유효한 제안이 없을 때의 연장 주기와 첫 게임 생성 검증 기준.
- 로그라이크 경계의 구체적인 판정 방법과 장르 내 상충하는 요구 처리. 개별 게임의 목표, 성장과 종료 조건 등은 참여자의 설계 영역이다.
- 초기 5~10분 목표의 지속 여부, 중간 저장 정책.
- 활동 시간 검증과 유사한 요구의 묶음 기준.
- 최신 버전의 기본 노출, 플레이 중 업데이트 알림 및 구버전에서 최신 버전으로 넘어가는 정책.
- 로컬 저장 삭제 또는 유실 대응, 장치 간 이동. 세이브는 버전별 독립이며 버전 간 이전은 하지 않는다.
- 업데이트 기준 시각과 다음 회차로 넘어간 요구 및 새 요구의 중복 처리 구현. 과거 점수 누적 없이 현재 회차 피드백을 우선하는 원칙은 확정되었다.
- Google 로그인 외 다중 계정 등 남용 방지, 공개 통계의 집계 단위와 노출 시점. 로그인 제공자는 Google로 확정했다.
- 자동 생성 변경의 검증 기준, 실행 격리, 재시도와 복구의 세부 동작.
- 생성한 Turso Starter DB의 세부 사용량 한도 확인과 운영 데이터 스키마·보관 범위. DB 생성과 production 환경변수 연결은 완료했다.
- 서비스·게임·아카이브의 상세 주소와 격리 구성. yourga.me의 기본 DNS·HTTPS 연결은 완료했다.
- 초기 실험 규모와 운영 기간, 로컬 작업자의 장애 감지와 복구 확인 방법.
- GitHub push로 시작하는 배포에서 '정해진 시각'이 배포 시작 목표인지 실제 공개 시각인지, 빌드 시간에 따른 공개 지연을 어느 정도 허용할지.
- 로컬 요청 전달 방식과 인증, 실제 Codex 비대화형 실행 지원 및 해당 이용 방식의 공식 지원 범위.
- 구독 포함 사용량만 사용하도록 중단하는 실제 통제와 하루 추가 AI 비용 1,000원 상한의 기술적 보장 가능 여부. 자동 유료 전환 및 추가 크레딧 구매는 하지 않는다.
- 게임이 나아졌는지 평가하는 기준.

## 이전 제안 중 채택하지 않은 방향

- 로그라이크를 벗어나 장르를 자유롭게 뒤집는 방향은 채택하지 않았다. 장르 안에서 규칙과 구조를 바꾸는 것은 허용한다.
- 충돌을 AI의 재량으로만 처리하는 방식은 채택하지 않았다. 여러 사용자의 피드백 가중치가 결정 근거가 되어야 한다.

## 변경된 합의

- 2026-08-31 요청에 따라 수집 회차당 참여자별 제안 하나 제한을 최근 60분 동안 신규 제출 최대 3개로 대체하고 제안당 2,000바이트 제한을 추가했다. 후속 Q3 답변으로 마감 전 수정 허용을 유지하고 삭제를 제외했다. 수정·삭제 모두 제외하자는 추천은 채택하지 않았다.
- 이번 개발 범위의 Q1 답변으로 최초 모집은 즉시 개시한다. 2026-09-01 00:00에 모집을 시작하고 04:00에 첫 게임을 공개하자는 추천은 채택하지 않았다. Q6 수락으로 8월 31일 23:00 모집 마감, 9월 1일 00:00 첫 공개 목표를 확정했다.
- 실패를 다음 정규 회차까지 조용히 넘기는 운영 대신, 확인 시 운영자에게 알리고 가능한 복구를 계속하는 요청을 수락했다. 안전 검사 우회, 인증 우회, 추가 유료 사용 또는 무한 재시도를 허용한다는 뜻은 아니다.
- 최초에는 배포를 기준으로 모든 참여자가 항상 동일한 버전을 경험한다고 정했으나, 이후 사용자가 이전 버전도 계속 플레이할 수 있는 아카이브를 요청했다. 따라서 최신 버전으로 전원 강제 전환하는 이전 추천은 채택하지 않는다.
- 하루 한 번 오후 9시에 배포하자는 추천은 채택하지 않았다. 사용자가 지정한 3시간 시작, 4버전마다 1시간 증가 규칙을 적용한다.
- Q6의 최초 핵심 목표·플레이 구조 보호 결정은 Q14의 수락으로 대체되었다. 이제 로그라이크 장르만 게임의 고정 경계로 두며, 이후 버전에서도 목표·전투·성장 구조 변경을 허용한다.
- 한 회차 최대 3개 반영 및 참여자에게 집계 점수·제외 사유를 설명하는 추천은 채택하지 않았다. 반영은 가급적 폭넓게 하고, 공개 화면은 순위 없는 요구 통계로 제한한다.
- 모바일에서 제안과 통계만 제공하는 절충안도 채택하지 않았다. 모바일 지원 전체를 범위에서 제외한다.
- 기존 DB 환경을 재사용하자는 추천 대신, 사용자가 직접 운영할 필요 없는 무료 온라인 관리형 DB를 요청했다. Supabase는 사용자 프로젝트 한도 때문에 제외한다.
- 무료 관리형 DB 비교 이후 GitHub·Vercel·Turso Free 구성을 수락했다. Vercel의 예약 기능 대신 PC의 처리 결과를 GitHub에 올려 Git 연동 배포를 시작한다.
- 동점 충돌을 최초 생성에서만 추첨하고 후속 버전에서는 보류하는 추천은 채택하지 않았다. Q31에서 점수가 다르면 추첨하지 않고, 동점이면 플레이타임 가중점수로 우선순위를 정한다고 명확히 했다. 기존 추첨 합의는 두 기준이 모두 같은 경우에만 남는다. 가중 추첨을 하자는 추천은 채택하지 않았다.

## 기술 검토 — 채택 여부와 미확인 사항

- [PC에서 시작하는 Git 연동 배포](deployment-flow.md): 배포 경로는 채택했다. push·빌드 완료·실제 공개를 구분하는 확인 절차를 정리했으며 예정 시각과 실제 공개 시각 사이의 지연 허용 여부는 미정이다.
- [무료 관리형 DB 비교](research/managed-database-options.md): 비교 후 Turso Free를 선택했다. 무료 한도, 실제 연동 플랜 및 사용량 설정은 연결 시 확인한다. Vercel Cron은 사용하지 않으며 PC가 처리 시점을 관리하고 GitHub push가 Vercel 배포를 유발한다.
- [Codex 구독을 사용하는 로컬 자동화 검토](research/codex-local-automation.md): 현재 PC의 CLI 설치와 ChatGPT 로그인은 확인했으며 실제 모델 작업은 실행하지 않았다. 공식 비대화형 실행 경로는 확인했지만, 이 서비스의 이용 허용 범위 및 크레딧을 포함한 엄격한 일일 비용 차단은 미확인이다.
- Vercel의 고유 배포 URL은 보존 정책이 허용하는 동안 접근할 수 있다. 구버전 플레이를 지속 제공하려면 배포 이력과 별개로 실행 가능한 빌드 및 자산의 보관·제공 방식을 정해야 한다. 출처: [고유 URL](https://vercel.com/docs/deployments/generated-urls), [보존 정책](https://vercel.com/docs/deployment-retention).
- GitHub Release는 빌드 파일 보관 후보지만, 다운로드 파일 보관과 웹에서 구버전을 계속 실행할 수 있게 제공하는 일은 별개다. 실제 저장 및 제공 구조는 아직 채택하지 않았다. 출처: [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
- 브라우저 저장소는 origin별로 나뉘므로, 다른 배포 도메인의 세이브를 자동 공유하지 않는다. 같은 도메인으로 여러 버전을 제공하면 버전별 저장 구분과 구버전 코드의 접근 범위도 설계해야 한다. 로컬 데이터는 브라우저 삭제나 저장소 퇴거로 유실될 수 있다. 출처: [MDN 저장소 경계와 보존](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- 로컬 세이브만을 근거로 공통 집계의 플레이타임 가중치를 검증할 수 있다고 가정하지 않는다. 최소 플레이 확인 기록을 중앙에 보관하기로 했으며, 이것만으로 조작 방지가 완성된다고 가정하지 않는다. 구체적 검증 방식은 미정이다.
- 생성된 게임 코드와 계정·제안·관리자 기능은 다른 보안 영역으로 격리해야 한다. 경로만 분리하면 브라우저 저장소 격리가 되지 않는다. 별도 origin, 서버 권한 검사, 쿠키 범위 및 CSRF 방어를 함께 검토한다. 출처: [동일 출처 정책](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [쿠키 범위](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- iframe sandbox와 로컬 세이브는 함께 설계한다. 같은 origin에서 allow-scripts와 allow-same-origin을 함께 허용하면 격리를 무력화할 수 있다. 모든 게임 버전에 하나의 origin을 쓰는 경우 버전별 세이브 이름만 달리하는 것은 버전 간 보안 격리가 아니다. 정확한 저장 중계 또는 버전별 origin 구조는 아직 채택하지 않았다. 출처: [iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), [postMessage 보안](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage).
- 서버가 활동 보고와 세션 상한을 관리하더라도 실제 사람이 플레이했음을 보증하지는 못한다. 활동 시간은 남용을 줄이도록 검증하는 가중치 산정 기록이며, 사람의 실플레이를 완전히 증명한 값으로 표시하지 않는다. 출처: [Chrome 로컬 저장소 편집](https://developer.chrome.com/docs/devtools/storage/localstorage).

## 구현 안전 조건

- 참여자의 게임 변경 자유를 인증, 가중치 계산, 관리자 권한, 배포 정책 변경 권한으로 확장하지 않는다.
- 프롬프트와 생성 게임 코드는 신뢰하지 않는 입력으로 취급하며, 게임 실행 영역에 운영 DB 자격증명이나 관리자 권한을 노출하지 않는다.
- 격리 및 자동 검증은 실제 구현에서 별도로 확인해야 한다. 문서 작성만으로 안전성이 검증되었다고 간주하지 않는다.
