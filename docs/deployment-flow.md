# PC에서 시작하는 Git 연동 배포

상태: 준비 페이지와 계정·제안·상태 API를 배포했고 5분 간격의 장애 점검·최초 공개 후속 실행을 등록했다. 실제 Google 로그인은 운영 origin 설정 오류가 남아 있다. 최초 제안 마감은 2026-08-31 23:00 한국시간, 첫 게임 공개 목표는 2026-09-01 00:00 한국시간이다. 게임 공개·버전 선택·자동 복귀 기능은 첫 게임 구현에 포함할 요구사항이며 아직 구현·검증하지 않았다. 실제 연결 현황은 [인프라 연결 상태](infrastructure-status.md)를 따른다.

## 역할과 경로

연결된 Turso Starter 월 $0 리소스에 제안과 회차 상태를 보관한다. 개인 PC가 확정된 회차를 가져와 Codex로 게임을 변경하고 로컬 검증을 수행한다. 검증된 코드를 연결된 GitHub 저장소의 운영 브랜치에 push하면 Vercel이 빌드와 배포를 시작한다.

GitHub의 hongwoogi/yourgame 비공개 저장소와 Vercel의 yourgame 프로젝트를 연결했다. main push에서 production 배포가 생성되고 yourga.me에서 준비 페이지가 HTTPS로 응답하는 것을 확인했다. Turso Starter DB yourgame을 production에 연결하고 계정·제안 스키마를 적용했다. 게임 API와 공개 이력 스키마는 아직 구현하지 않았다.

Vercel Cron은 사용하지 않는다. 현재 작업의 5분 간격 Codex 후속 실행이 상태 점검과 최초 공개 절차를 이어간다. 매 회차 사람이 배포 버튼을 누르는 절차를 요구하지 않는다. 후속 실행 등록이 정시 실행이나 게임 자동 진화 전체의 구현을 뜻하지는 않는다.

운영 브랜치는 Vercel의 Production Branch 설정으로 결정되며 현재 연결에서는 main이다. main push로 production 배포가 생성되는 것을 확인했다. 다른 브랜치는 기본적으로 preview 배포 대상이므로 작업용 브랜치의 배포 성공을 새 게임 공개로 집계하지 않는다. 준비 페이지 배포도 게임 v1 공개나 최초 모집 시작으로 집계하지 않는다. [Vercel Git 연동](https://vercel.com/docs/git)

## 권장 완료 확인

1. 회차별 최종 커밋을 고정하고 로컬 검증 결과를 보관한다.
2. PC가 운영 브랜치에 push한 뒤 상태를 배포 진행 중으로 기록한다.
3. 예상 프로젝트, production 환경, 커밋 SHA에 해당하는 배포 결과를 조회한다.
4. 성공한 해당 배포가 실제 운영 도메인에 연결되었는지 확인하고, 도메인에서 버전 식별자와 기본 실행 상태를 검사한다.
5. 공개 확인을 통과했을 때만 회차를 공개 성공으로 기록하고 버전 집계와 기여 이력을 한 번 갱신한다.

push 성공이나 READY 상태만으로 공개 완료를 판단하지 않는다. READY인 preview 또는 아직 운영 도메인에 연결되지 않은 배포가 있을 수 있다. 현재 운영 도메인이 연결된 배포와 예상 커밋을 함께 확인한다. [운영 배포 상태](https://vercel.com/docs/deployments/promoting-a-deployment#production-deployment-state), [배포 검증](https://vercel.com/docs/deployments/promote-preview-to-production)

기본 Git 연동에서는 Vercel이 빌드를 마치고 공개한 뒤 PC가 이를 확인하게 된다. 공개 후 실행 검사는 공개 전 차단 장치가 아니므로 게임 후보 배포와 현재 제공 게임의 전환을 분리한다. 공개 전 실패는 기존 정상 게임을 유지하고, 새 게임을 제공한 뒤 확인된 장애는 마지막 정상 게임으로 자동 복귀하는 정책으로 확정했다. 앱 배포 성공과 게임 공개 성공도 구분한다.

상태 확인을 재시도해도 버전 번호나 기여 이력이 중복 갱신되지 않게 한다. 다음 공개가 진행 중인 공개와 겹치지 않도록 직렬 처리한다. 같은 브랜치에 후속 커밋을 연이어 올리면 이전 대기 빌드가 생략될 수 있으므로 공개하려는 커밋을 명확히 추적한다. [Vercel 빌드](https://vercel.com/docs/builds)

## 시간과 실패 처리

기존 합의인 초기 3시간 간격과 성공한 공개 버전 4개마다 간격 1시간 증가 규칙은 유지한다. 정규 배포 1시간 전에 제안과 가중치를 확정하고 제작·검증을 수행한다.

다만 GitHub push 시각과 실제 공개 시각은 같지 않다. 현재 경로에 가장 단순하게 맞는 안은 예정 시각에 배포를 시작하고 Vercel 빌드가 완료되는 대로 공개하는 것이다. 이 지연 허용 여부는 아직 사용자에게 확인하지 않았다.

정확한 공개 시각이 필요하다면 사전에 production 빌드를 완료하고 공개 단계만 분리하는 구조를 검토해야 한다. 일반 preview 배포의 production 승격은 재빌드될 수 있으므로 이를 같은 방식으로 가정하지 않는다. 공개 단계만 분리해도 플랫폼·네트워크 지연까지 없어지는 것은 아니다. [배포 승격 방식](https://vercel.com/docs/deployments/promoting-a-deployment)

PC 응답 없음, 구독 한도 부족, 로컬 검증 실패 또는 공개 전 배포 실패 시 기존 정상 게임을 유지한다. 공개 후 새 게임의 장애가 확인되면 마지막 정상 게임으로 자동 복귀한다. 복귀 후 실제 제공 상태를 검사하기 전에는 복구 완료로 표시하지 않는다. 이전 정상 게임이 없는 최초 공개 실패에는 준비 화면과 지연 안내를 제공한다. 참여자 안내는 [운영 상태 문구](operations-status.md)를 따른다.

사용자의 2026-08-31 요청에 따라 실패가 확인되면 이 작업에 알리고 가능한 복구를 즉시 시작한다. 다음 정규 회차까지 조용히 넘기지 않으며, 공개 목표를 맞추기 위해 검증을 생략하지 않는다. 초기 자정 시각은 첫 게임의 공개 목표이지 성공 보장 시각이 아니다.

## 마지막 정상 게임 유지와 자동 복귀

아래는 첫 게임 공개 전에 구현·검증할 요구사항이다. 현재 운영 앱의 커밋이나 상태 모니터의 정상 버전 기록은 정상 게임의 증거가 아니며, 지금은 복귀할 공개 게임이 없다.

1. 공개 게임의 실행 파일·자산은 버전별로 보존한다. 게임 ID, 자산 체크섬, 소스 커밋, 해당 고유 배포 ID, 검증 시각과 현재 제공 버전을 기록한다. 다음 전환 전에는 복귀 대상의 자산과 실행 상태가 여전히 정상인지 확인한다.
2. 후보를 배포해도 현재 제공 게임은 검증이 끝날 때까지 유지한다. 제작·검증·배포가 실패하면 해당 공개 시도만 실패로 기록하고 정상 게임과 그 버전 번호를 그대로 제공한다.
3. 공개 후 새 게임에 원인이 있는 실행 장애가 확인되면 기록된 마지막 정상 게임으로 제공 대상을 되돌린다. 공개와 복귀를 직렬 처리하고 실패 시도별로 한 번만 전환한다. 요청 결과가 불명확하면 상태부터 조회하며 무한 재시도나 반복 전환을 하지 않는다.
4. 운영 도메인에서 실제 게임 ID·자산과 실행·입력·종료 동작을 확인한 뒤에만 복귀 완료로 기록한다. 복귀 검증이 실패하거나 결과가 미확인이라면 장애 게임의 새 플레이와 후속 공개를 중단하고 운영자에게 알린다. 화면에는 실패한 공개 시도와 현재 제공 중인 정상 게임을 구분한다.
5. 게임 복귀로 계정·제안·제출 횟수·DB·기여 이력·버전별 세이브를 되돌리지 않는다. 철회한 게임은 복구 확인 전 새 플레이를 막고, 다른 버전의 세이브를 덮어쓰지 않는다. 이미 공개된 버전 번호와 실패 이력도 보존한다.

복귀 자체는 새 공개 성공이나 버전 증가가 아니다. 공개 전에 실패한 시도는 성공 집계에 넣지 않는다. 현재 제공 버전과 누적 공개 이력은 별도 값으로 관리한다.

Google origin 설정 오류나 DB 제공자 장애처럼 게임 변경과 무관한 문제는 이 복귀로 해결되지 않는다. 그 문제는 별도 장애로 유지하고, 이전 준비 페이지로 앱 전체를 되돌려 접수 기능을 없애는 식으로 처리하지 않는다.

## 전체 앱 배포를 되돌려야 할 때

게임 제공 대상만 바꾸는 것으로 복구할 수 없는 앱 코드 회귀에 한해 검토한다. 이전 배포의 코드·환경설정이 현재 DB 스키마와 데이터에 호환되는지 먼저 확인한다. 앱 배포 복귀는 DB, Google 설정, 로컬 후속 실행을 함께 되돌리지 않는다.

- 현재 Hobby 플랜의 Instant Rollback 대상은 바로 직전 운영 배포로 제한된다. 그 배포가 마지막 정상 게임을 담고 있다고 가정하지 않는다. 게임 복귀를 임의의 과거 앱 배포 롤백에 의존하지 않는다. [Vercel 롤백 제한과 외부 서비스 주의사항](https://vercel.com/docs/instant-rollback)
- 실행할 때는 검증한 고유 `dpl_…` ID 또는 고유 배포 URL을 지정한다. 이동하는 운영 도메인이나 커밋 SHA를 대상으로 쓰지 않는다. 현재 CLI에서 인수 없는 `vercel rollback`은 상태 조회이므로 실제 복귀로 기록하지 않는다. 제한 시간을 넘겼으면 요청 상태부터 확인해 중복 실행을 피한다. [CLI 롤백](https://vercel.com/docs/cli/rollback)
- 롤백 뒤에는 Git push로 빌드가 생성되어도 운영 도메인 자동 할당이 중단된다. 검증된 수정 배포를 명시적으로 승격해야 자동 할당이 재개된다. 장애 후보를 다시 자동 공개하지 말고, 승격 전까지 후속 공개를 보류한다. [롤백 후 정상 배포 재개](https://vercel.com/docs/instant-rollback#undo-a-rollback)
- CLI 종료 코드만으로 완료 처리하지 않는다. 실제 운영 도메인의 배포 ID, `/api/health`의 앱 버전, 현재 제공 게임의 동작을 모두 확인하고 결과를 기록한다.

## 무료 운영의 제약

Git push로 시작하는 배포에도 일반 빌드·배포·함수 사용량 한도는 적용된다. Vercel Cron을 사용하지 않는다고 다른 사용량 제한까지 없어지는 것은 아니다. [Hobby 플랜](https://vercel.com/docs/plans/hobby)

Vercel Account Webhooks는 Pro/Enterprise 기능이므로 Hobby 구성의 필수 전제로 삼지 않는다. 로컬 작업자는 제한적인 배포 상태 조회와 실제 운영 URL 확인을 기본안으로 사용한다. [Vercel Webhooks](https://vercel.com/docs/webhooks)

이 경로만으로 구버전 플레이 아카이브가 영구 보존되지는 않는다. 실행 가능한 과거 빌드와 자산의 보관·제공 방식은 별도로 정한다.
